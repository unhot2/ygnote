## 1. 원본 데이터 구조 확인 결과

### 1.1 컬럼 (6개, 헤더 그대로)

| 컬럼명 | 내용 | 비어있는 행 |
|---|---|---|
| 날짜 | `10/24(토)` 형식 (요일 포함 텍스트) | 없음 |
| 시간 | `오전 11:30` / `오후 2:00` 형식 텍스트, 일부 비어있음(자유시간 등) | 다수 |
| 일정 | 일정명 텍스트 (예: "신신라멘 텐진 본점", "인천 → 후쿠오카 출발") | 1곳 |
| 주소 | 구글 지도에서 복사한 도로명 주소 텍스트. **좌표 없음, 일부 행만 존재** | 대부분 비어있음 (25행 중 6행만 존재) |
| 비고 | 자유 서술형 메모 (리뷰, 당부, 준비물 성격 설명 등) | 다수 |
| 준비 사항 | 예약 여부 등 (현재 "예약 완료" 2건만 존재) | 대부분 비어있음 |

### 1.2 중요하게 반영해야 할 특징

- **카테고리 컬럼이 없다.** 마트/가게/식당/교통/숙박 구분은 시트에 명시돼 있지 않고 "일정" 텍스트와 "비고"에서 추론해야 한다.
- **좌표가 없다.** 주소는 사람이 읽는 도로명 주소 텍스트(구글맵에서 복사한 형태, 일부는 일본어/영문 혼용)뿐이다. 지도 표시를 위해서는 지오코딩(주소→좌표 변환)이 필요하다.
- **주소가 있는 일정이 오히려 적다.** 25개 일정 중 주소가 있는 건 6개뿐(라멘집, 마트, 에어비앤비, 나카스 거리, 이비자 클럽, +1). 나머지는 지명만 텍스트로 있거나(텐진 포장마차 거리, 동네 이자카야) 이동/교통 일정이라 주소 자체가 없다.
- **영업시간, 전화번호 등 "상세정보"는 시트에 전혀 없다.** AC-25 요구사항의 "마트·가게의 상세 정보(영업시간, 주소 등)"는 현재 시트 범위를 벗어나므로, 이번 디자인에서는 **상세정보 영역의 틀만 설계**하고 데이터는 추후 별도로 입력/연동(예: 구글 플레이스 API 또는 수동 입력 컬럼 추가)하는 것으로 범위를 분리한다.
- **일본어 표현 데이터도 시트에 없다.** 장소 카테고리별로 큐레이션된 표현 세트를 별도 데이터로 설계해야 한다(아래 4장).

### 1.3 제안: 카테고리 추론 규칙 (시트 원본은 건드리지 않고, 프런트엔드 매핑 테이블로 분류)

| 카테고리 | 판별 키워드 (일정/비고) | 예시 |
|---|---|---|
| 교통/이동 | 출발, 도착, 버스, 공항, 비행, 택시 | 인천→후쿠오카, 고속버스, 버스터미널로 출발 |
| 식당/주점 | 라멘, 포장마차, 이자카야, 클럽, 가이세키 | 신신라멘, 나카스 포장마차 거리, 동네 이자카야 |
| 마트/상점 | 마트, Foods Club | Iseya Foods Club 마트 방문 |
| 숙박 | 체크인, 체크아웃, 에어비앤비, 료칸, 호텔 | 에어비앤비 체크인, 료칸 체크인 |
| 자유시간/관광 | 자유시간, 산책, 온천, 족욕 | 온천마을 산책·카페·족욕 |

> 참고: 정확도를 높이려면 시트에 "카테고리" 컬럼을 추가하는 걸 권장하지만, 이번 디자인 단계에서는 시트 수정 없이 프런트엔드 매핑으로 처리하는 걸 기본안으로 한다. (구현 단계에서 사용자 확인 필요)


- 좌측 패널: 날짜별로 그룹핑된 세로 타임라인. 각 항목에 시간 + 일정명 + 카테고리 아이콘(교통/식당/마트/숙박/자유시간)을 표시.
- 우측 패널: 세로로 3개 영역(지도 / 상세정보 / 일본어 표현)이 쌓이는 구조. 선택한 일정의 상태에 따라 상세정보 카드는 보이거나 숨겨진다.
- 모바일(좁은 화면) 대응은 이번 디자인 범위에 포함하지 않음 — 필요 시 별도 작업으로 분리 제안.

## 3. 화면 상태 정의

### 상태 A. 일정 선택 전 (초기 진입)

- 좌측: 전체 일정 목록 표시, 아무 항목도 하이라이트되지 않음.
- 우측 지도: 여행 전체 범위(후쿠오카~구로카와)를 보여주는 기본 뷰. 주소가 있는 모든 일정의 핀을 흐리게 전체 표시(선택 유도).
- 상세정보 카드: 숨김.
- 일본어 표현 카드: "여행 전체에서 자주 쓰는 표현" 기본 세트 표시 (인사, 숫자, 결제 관련 등 공통 표현).

### 상태 B. 일정 선택 후 — 주소가 있는 경우

- 좌측: 선택한 항목 하이라이트.
- 우측 지도: 해당 주소로 확대 이동, 핀 표시 + 장소명 라벨.
- 상세정보 카드: 카테고리에 따라 표시 여부 분기 (아래 상태 C/D 참고).
- 일본어 표현 카드: 해당 일정의 카테고리에 매칭되는 표현 세트로 전환.

### 상태 C. 일정 선택 후 — 주소가 없는 경우 (예: 텐진 포장마차 거리, 동네 이자카야, 이동 일정)

- 우측 지도: 핀을 꽂을 수 없으므로 "정확한 위치 정보가 아직 없어요" 안내 문구 + 느슨한 지역명(예: "후쿠오카 텐진 일대") 정도의 대략적 중심 표시, 또는 지역 수준 지도만 보여줌.
- 상세정보 카드: 숨김 (주소/영업시간 등 표시할 데이터가 없으므로).
- 비고 내용(있다면)은 일정 목록 항목 아래 짧은 메모로 유지 표시.
- 일본어 표현 카드: 카테고리 추론이 가능하면 그대로 표시(예: 이자카야 → 식당 표현), 교통/이동류는 "교통/길찾기 표현" 세트로 전환.

### 상태 D. 상세정보가 필요한 카테고리 (마트, 가게, 식당, 이자카야, 클럽)

- 상세정보 카드 표시. 표시 항목(섹션 4.2 참고):
  - 장소명
  - 주소 (시트 원본 값)
  - 영업시간 — **현재 데이터 없음 → "정보 준비 중" 플레이스홀더로 표시**
  - 전화번호 — **현재 데이터 없음 → 플레이스홀더**
  - 비고 (시트 원본 "비고" 컬럼 값 그대로, 있는 경우만)
  - 준비 사항 (시트 원본 값, 있는 경우만. 예: "예약 완료")

### 상태 E. 상세정보가 필요 없는 카테고리 (교통/이동, 숙박 체크인·체크아웃, 자유시간)

- 상세정보 카드 숨김.
- 대신 좌측 목록 항목 또는 지도 하단에 "이동 정보" 미니 라인만 표시 (예: "항공편 · 고속버스 · 택시" 등 비고 값 그대로).

## 5. 다음 단계에서 판단/결정이 필요한 사항 (구현 착수 전 확인 요청)

1. **카테고리 컬럼**: 시트에 "카테고리" 컬럼을 직접 추가할지, 프런트엔드 추론 로직으로만 처리할지.
2. **지도 API 선정**: 구글 맵 / 네이버 지도 / 카카오맵 중 선택 (API 키 발급, 과금 정책 확인 필요).
3. **지오코딩 방식**: 빌드 타임에 주소→좌표를 미리 변환해 저장할지, 런타임에 호출할지.
4. **영업시간/전화번호 데이터 소스**: 수동 입력(시트에 컬럼 추가) vs 지도 API의 장소 정보 연동(Google Places 등).
5. **일본어 표현 데이터**: 별도 JSON/시트로 관리할지, 코드 내 상수로 관리할지.
